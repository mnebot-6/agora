# Pagos con Stripe — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Que un miembro pague su plaza con tarjeta desde Android y desde web, que el dinero vaya a la cuenta de Stripe del admin de su comunidad sin pasar por Agora, y que liberar una plaza devuelva el dinero en cuanto otro la pague.

**Architecture:** Stripe Connect Standard con cargos directos. Tres Edge Functions de Supabase guardan la clave secreta (`stripe-connect`, `stripe-checkout`, `stripe-webhook`) más un barrido (`stripe-sweep`) que reconcilia lo que se quede a medias. El cliente nunca ve un dato de tarjeta: sale a Stripe Checkout en el navegador y vuelve por deep link. Una tabla `payments` registra cada cobro y un índice único parcial sobre ella es el cerrojo que impide dos pagos por la misma plaza.

**Tech Stack:** Kotlin Multiplatform + Compose Multiplatform, Voyager (ScreenModel), Koin, supabase-kt (postgrest RPC + functions), Supabase Edge Functions (Deno), Supabase CLI para migraciones, pg_cron, Cloudflare Workers para el dominio, kotlin-test.

**Spec:** `docs/superpowers/specs/2026-08-19-stripe-design.md` (aprobado el 2026-08-19)

## La trampa que condiciona todo el orden

`SlotStatus` es un enum **cerrado y sin fallback**:

```kotlin
// core/model/.../Slot.kt — hoy
@Serializable
enum class SlotStatus {
    @SerialName("available") AVAILABLE,
    @SerialName("reserved") RESERVED,
    @SerialName("paid") PAID,
    @SerialName("pending") PENDING,
}
```

En el momento en que la base de datos devuelva `pending_payment`, `decodeList<Slot>()` lanza excepción y **tumba la lista entera de plazas**, no la fila mala. En todos los clientes que no se hayan actualizado. En producción.

Es exactamente la misma mina que ya explotó con `NotificationType`, que hoy tiene `UNKNOWN` y un serializer propio con el comentario "load-bearing: no los quites". A `SlotStatus` nadie se lo aplicó.

**Consecuencia para este plan:** la Task 1 arregla la tolerancia del enum y **tiene que estar publicada en Play y en web antes de que la migración de la Task 2 toque producción**. No es una recomendación de estilo, es la diferencia entre desplegar y romperle la app a todo el mundo.

Solo `SlotStatus` está en riesgo. El resto de enums del modelo (`SlotMode`, `ActivityStatus`, `MemberRole`, `JoinRequestStatus`, `GuestRequestStatus`, `CommunityVisibility`) también son cerrados y sin fallback, pero **este trabajo no les añade valores**, así que se quedan como están. Arreglarlos es una limpieza aparte.

- [ ] **Step 2: Enum tolerante**

En `Slot.kt`, sustituir el enum por el patrón de `NotificationType` (serializer propio con `wire`):

```kotlin
/**
 * El servidor puede empezar a emitir estados nuevos antes de que la app se actualice. Con un enum
 * cerrado, decodeList tumba la lista ENTERA de plazas ante un valor desconocido. UNKNOWN y su
 * serializer son load-bearing: no los quites.
 */
@Serializable(with = SlotStatusSerializer::class)
enum class SlotStatus(val wire: String) {
    AVAILABLE("available"),
    RESERVED("reserved"),
    PAID("paid"),
    /** Plaza retenida por un invitado a la espera de aprobacion de un admin. */
    PENDING("pending"),
    /** Alguien tiene el Checkout abierto sobre esta plaza. */
    PENDING_PAYMENT("pending_payment"),
    UNKNOWN("unknown"),
}

object SlotStatusSerializer : KSerializer<SlotStatus> {
    private val byWire = SlotStatus.entries.associateBy { it.wire }

    override val descriptor: SerialDescriptor =
        PrimitiveSerialDescriptor("SlotStatus", PrimitiveKind.STRING)

    override fun serialize(encoder: Encoder, value: SlotStatus) = encoder.encodeString(value.wire)

    override fun deserialize(decoder: Decoder): SlotStatus =
        byWire[decoder.decodeString()] ?: SlotStatus.UNKNOWN
}
```

### Task 8: Las transiciones compartidas y el webhook

El webhook y la sincronización por deep link **tienen que ejecutar el mismo código**. Si son dos implementaciones, divergen, y el día que diverjan alguien se queda cobrado sin plaza.

**Files:**

- [ ] **Step 1: `applyPaymentSucceeded(paymentId, session)`**

Idempotente por construcción. En una transacción:

```
UPDATE payments SET status='succeeded', payment_intent_id=..., charge_id=...
WHERE id = paymentId AND status = 'pending'
-- si no afecta a ninguna fila: ya estaba aplicado, salir sin hacer nada mas

UPDATE slots SET status='paid', reserved_by=<pagador>, reserved_at=now(),
                 hold_expires_at=NULL, released_at=NULL,
                 offered_to=NULL, offer_expires_at=NULL
WHERE id = <slot>

DELETE FROM substitute_queue WHERE activity_id=... AND user_id=<pagador>

-- si habia un pago anterior en esa plaza esperando sustituto, marcarlo para reembolso
UPDATE payments SET status = CASE WHEN method='stripe' THEN 'refund_pending' ELSE 'refund_owed' END,
                    refund_reason='substitute'
WHERE slot_id=<slot> AND status='awaiting_substitute'

INSERT INTO notifications ...  -- 'payment_confirmed' al pagador
```

El `AND status = 'pending'` del primer `UPDATE` es lo que hace idempotente todo el bloque: el segundo evento no afecta a ninguna fila y se sale antes de tocar nada más.

- [ ] **Step 2: `applyPaymentNotCompleted(paymentId)`**

```
UPDATE payments SET status='expired' WHERE id=paymentId AND status='pending'
-- si no afecta a ninguna fila, salir

UPDATE slots SET status='available', reserved_by=NULL, reserved_at=NULL, hold_expires_at=NULL
WHERE id=<slot> AND status='pending_payment' AND reserved_by=<pagador>
```

## Qué NO hace este plan (a propósito)

- **No borra `cost_description`.** Se deja de escribir y se sigue leyendo como ayuda. Se elimina en una migración posterior, cuando no quede nadie usándolo.
- **No parsea los importes antiguos.** Sacar "6,50" de "Bizum de 6.5 euros por persona" es una lotería y equivocarse en dinero es lo peor que puede hacer una migración.
- **No cobra a los invitados.** El flujo anónimo web se queda con cobro manual, tal como se decidió.
- **No pone comisión a Agora.** `PLATFORM_FEE_BPS=0`. El código de la comisión existe y funciona; el valor arranca a cero.
- **No hace facturas ni recibos fiscales.**
- **No permite precios distintos por posición o por grupo.** Precio único por actividad.
- **No permite pedir un reembolso.** La única vía es que otro ocupe tu plaza.
